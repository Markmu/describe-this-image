# Service configuration

The local site runs with `pnpm dev` at http://localhost:3000. Sample previews work without service credentials. Image generation, authenticated usage and payments require the settings below; missing settings produce an unavailable state.

## Database and usage
Set DATABASE_URL in `.env.local` to a PostgreSQL database owned by this application, then run `pnpm db:migrate`. The migration creates tables without dropping data. Back up a populated database before migrations. Development reads `.env.local` through Next.js; the migration, recovery and billing test commands load it through Node.js (22.9 or later). Exported variables take precedence.

The local Docker container `describe-audit-db` publishes PostgreSQL at `127.0.0.1:5434`, mapped to container port `5432`, with restart policy `unless-stopped`. Use port `5434` in both `.env.local` connection URLs: `DATABASE_URL` selects `describe_local`, and `TEST_DATABASE_URL` selects `describe_audit`. Start or restart it with `docker start describe-audit-db` or `docker restart describe-audit-db`. When recreating the container, reuse its PostgreSQL data volume and specify `--publish 127.0.0.1:5434:5432`; omitting the host port lets Docker assign a changing port. Restart the development server after changing `.env.local`.

Each image generation costs 10 credits and returns all four description formats. Guests receive 10 credits (one image) per signed trial identity, subject to one new guest grant per trusted IPv4 address or IPv6 /64 network. New guest sessions use a domain-separated, source-derived bootstrap UUID, so concurrent first visits and cookie deletion resolve to the same trial identity and balance. Existing valid signed cookies retain their owner, including when the network changes. A database claim binds the first eligible guest owner to that network source and prevents another owner from receiving a fresh grant. Shared networks share a trial; Google sign-in provides separate account welcome credits. Each signed-in Google account receives 20 non-expiring welcome credits (two images) once. There is no daily refill; guest and account balances remain separate. Existing guest grants and refunds retain their recorded balances, including multiple grants issued before migration 006; the source gate constrains new issuance rather than revoking prior entitlements. A guest owner changing networks keeps its balance and cannot claim a second grant. Source claims remain with the quota ledger and are excluded from telemetry cleanup.

Anonymous usage and generation require `TRUSTED_CLIENT_IP_HEADER` to name a header that ingress overwrites with one bare client IP address. Block direct access that bypasses that ingress. Forwarding lists, ports, brackets, zone identifiers and malformed addresses are rejected. Equivalent IPv6 forms and IPv4-mapped IPv6 addresses share the same source; IPv6 host changes within a /64 do not create a new source. Source keys are domain-separated HMACs under `AUTH_SECRET`; raw addresses are not stored. Keep this secret consistent across workers. Secret rotation changes source keys and requires a deliberate claim migration or acceptance of a renewed source budget. Missing header configuration or a missing header returns 503 for anonymous requests; malformed addresses return 400. There is no shared fallback bucket. Signed-in usage and account history require no client IP header.

`GET /api/usage` can issue an allowance, so it also requires a matching `Origin` or browser Fetch Metadata with `Sec-Fetch-Site: same-origin` / `none`. Cross-site requests, foreign origins and requests without either proof return 403 before authentication, throttling or quota writes. Same-origin browser fetches work without an `Origin` header; non-browser clients must supply the application origin. This prevents browser cross-site requests from occupying a victim's source claim; it is not bot authentication.

Generation has persistent fixed-hour throttles (30 requests per anonymous network source, 120 per signed-in account). Usage reads have a separate 300/hour throttle. Different network prefixes or Google accounts remain distinct identities; these controls do not establish person-level uniqueness. Enforce request size, rate, concurrency and total provider-spend limits at ingress/provider accounts as well. Production header overwrite and origin isolation must be verified at deployment. For local anonymous testing, use an isolated loopback-bound server with a test-only source header; do not expose a caller-controlled test header on a public deployment.

Apply migration 006 before starting this code, and stop old grant-writing workers during cutover. Older workers do not enforce source claims. Apply migrations to both the development and isolated integration-test databases.

Apply all migrations before deploying this usage policy. Migration 003 adds the welcome grant kind while retaining historical daily grants and ledger entries. Existing daily grants are excluded from available balances and spending. The first usage read grants welcome credits to each account; later reads and later days do not grant more. Welcome credits are spent before paid credits. Migration 004 converts the previous 1-credit guest and 2-credit welcome grants to the 10-credit image denomination, preserving the number of free images left. It retains prior ledger entries and adds balance conversion entries. Pending reservations created before migration retain their original denomination for refunds. Purchased and subscription balances keep their stored credit amounts.

Run `pnpm usage:recover` with DATABASE_URL configured to refund reservations left pending for more than five minutes after a process crash. Run this through the deployment scheduler. The safety check has a 30-second deadline, followed by a model request timeout of 45 seconds. The description route and browser allow 90 seconds; configure ingress and hosting limits to match. Recovery processes up to 500 reservations per invocation.

## Google
Generate a private AUTH_SECRET (at least 32 characters), set AUTH_GOOGLE_ID and AUTH_GOOGLE_SECRET, and register:
- Development redirect: http://localhost:3000/api/auth/callback/google
- Deployment redirect: https://YOUR_DOMAIN/api/auth/callback/google

Set AUTH_URL and NEXT_PUBLIC_APP_URL to the intended origin. Enable AUTH_TRUST_HOST only behind ingress that validates and overwrites forwarded host headers. Rotate the former published development secret in every deployment; local configuration has been rotated without printing its value. Google accounts must have verified email. The server uses Google's subject identifier for ownership.

## Image descriptions
Set a private Gemini VISION_API_KEY and an explicit VISION_MODEL supporting image input and JSON structured responses. Select the model from your enabled Google project. The implementation sends a metadata-stripped PNG of at most 1536 pixels per side. Inputs support JPEG, PNG, WebP and GIF up to 10 MB / 40 megapixels. GIF generation uses the first frame. Review Google's processing and retention terms before publishing the privacy notice.

Remote image URLs are loaded by the browser with CORS, omitted credentials and blocked redirects. The server has no URL-fetch proxy. Image hosts must permit cross-origin browser reads.

## SeeAPI image safety
Set a private `SEEAPI_API_KEY`. Every generated description requires a successful [SeeAPI NSFW Filter 2.0 image moderation check](https://www.seeapi.com/docs/nsfw-filter-2/image-moderation/). Missing credentials or an invalid threshold disable generation, including batch processing. Sample previews remain available.

`SEEAPI_NSFW_THRESHOLD` defaults to `0.5` and accepts finite values from `0.01` to `0.99`; lower values tighten detection. `strict_special_care` is fixed to `true`. The policy blocks flagged results and any `nudity`, `sexual_activity`, `sexual_suggestive` or `sexual_minors` labels. Medical, breastfeeding and artistic images can be blocked under this policy.

After input validation and credit reservation, the server creates a metadata-free 1536 × 1536 PNG copy with a white background and letterboxing. This preserves the frame, supports small and narrow inputs, and fits the provider's recommended dimensions, pixel count and file limit. Original URLs are not sent to SeeAPI. Requests use `POST https://api.seeapi.com/v1/inferences`, the reservation ID as the basis of a stable `Idempotency-Key`, and the model/endpoint/provider identifiers `nsfw-filter-2` / `image-moderation` / `seeapi`. The server polls `GET /v1/inferences/{id}` with backoff, honors `Retry-After`, and accepts only a terminal `succeeded` task with a valid, unflagged JSON result and empty category arrays. A processing task or null result never counts as a pass.

Blocked images return HTTP 422 with `CONTENT_BLOCKED`. Provider failures, malformed responses and timeouts return HTTP 503 with `MODERATION_UNAVAILABLE`. Both stop the Gemini call and refund the credit reservation. In a batch, a content rejection marks the image blocked and continues the queue; blocked entries are excluded from retries and CSV exports. A safety service failure stops the queue. Existing hourly throttles apply to rejected attempts. Operational records store request metadata and a passed/blocked summary; images, category payloads and provider response bodies are excluded. Review SeeAPI's processing and retention terms for deployment.

Contract and workflow tests use fixtures without paid API calls. This checkout has no SeeAPI credentials; a live check remains a deployment verification step.

## Creem
Set CREEM_ENVIRONMENT to test or live and use matching API key, signing secret and product IDs:
- CREEM_PRODUCT_STARTER: USD 699 cents ($6.99), one time, 500 non-expiring credits (50 images).
- CREEM_PRODUCT_PRO_MONTH: USD 990 cents ($9.90), every month, 2,000 credits per month (200 images).
- CREEM_PRODUCT_PRO_YEAR: USD 7990 cents ($79.90), every year, twelve monthly windows of 3,000 credits (300 images per month, 3,600 per year).

Add-on is retired: new checkout requests reject its offer ID. Keep historical orders and their provider records for fulfillment and refunds; already-purchased credits remain valid. The server reconciles Starter payments using each stored order amount, including the previous $9.99 price. Configure the current Starter product at 699 cents and bind its product ID through CREEM_PRODUCT_STARTER before enabling checkout.

New Starter orders snapshot 500 credits. Existing Starter orders retain their stored 300-credit entitlement, including pending payments and refunds. Migration 004 keeps the historical 300-credit backfill. Update the Creem product description to 500 credits / 50 image descriptions while retaining the $6.99 one-time price.

Migration 004 snapshots each existing order's credit entitlement in `billing_orders.credit_amount`. Previous $49.90 annual orders retain twelve windows of 2,000 credits. New $79.90 annual orders snapshot 3,000 credits per monthly window. Renewals and delayed webhooks use the stored order price and credit amount. Do not reprice or rebind historical provider orders. A pending checkout with old terms is not resumed as a new-price checkout.

For this schema upgrade, stop old application workers before running `pnpm db:migrate`, then start the new version. Old checkout writers do not populate the required order-credit snapshot. Keep the old Creem annual product for existing subscriptions and configure a separate $79.90 annual product for new checkouts.

Configure active products without trials, seat multipliers or discounts. The checkout validates product price, currency, billing type and interval. Unadvertised product configuration fails closed. Subscription credits expire at the next monthly boundary; annual credits do not become usable as a single 36,000-credit balance. Cancellation retains Pro access through the paid period. Refunds, including partial refunds, or disputes revoke the remaining credits for that transaction; consumed credits are not restored. Review partial refunds through support.

Register the POST webhook https://YOUR_DOMAIN/api/webhooks/creem for checkout.completed, subscription.paid, subscription.active, subscription.canceled, subscription.scheduled_cancel, subscription.past_due, subscription.unpaid, subscription.expired, subscription.update, subscription.paused, refund.created and dispute.created. Do not use checkout redirects to grant credits.

For local sandbox testing, create a test webhook with delivery mode `cli` and the same event list. Store its ID as `CREEM_WEBHOOK_ID` and its signing secret as `CREEM_WEBHOOK_SECRET` in `.env.local`, alongside the test API key and three product IDs. Run `pnpm dev` and `pnpm billing:listen` in separate terminals. The listener forwards Creem's signed event bodies to `/api/webhooks/creem` on the loopback `NEXT_PUBLIC_APP_URL`, checks that the signing secret matches, and omits the secret from its startup output. Keep it running while testing; restart it after changing the configuration. The persistent endpoint remains available after the listener stops. Production uses an HTTPS webhook with HTTP delivery instead.

The webhook verifies raw-body HMAC, reads provider evidence, binds local order/product/environment/customer, and writes events, transactions and credit grants in one database transaction. Retries return duplicate acknowledgments without repeating grants. Unknown payment reversals return a retryable error while reconciliation is pending. Paid subscriptions use subscription.paid. A pending checkout with a known URL can be resumed for the same Pro offer; an uncertain provider failure requires receipt/order reconciliation before starting another subscription.

Use Manage billing in the signed-in account menu or the portal link in a Creem receipt. The portal route chooses the authenticated user's stored customer identifier; clients cannot supply another customer.

Before accepting live payments, exercise Google login, initial payment, duplicate webhook delivery, renewal, canceled access through period end, refund, dispute and portal cancellation in Creem test mode. The local sandbox checkout, credit fulfillment, refund, portal cancellation and payment replay results are recorded in [the 2026-11-10 sandbox report](testing/creem-sandbox-2026-11-10/README.md). Provider renewals across billing periods, disputes, partial refunds and production deployment remain release checks.

## Account pages

`/account/plans` reads available credits, their source grants, the next monthly window, and credit activity. `/account/billing` reads the subscription, pending checkouts, and payment transactions. Both pages require a server-verified session, disable indexing and shared caching, and preserve an allowlisted account destination through sign-in. The Account menu links to these pages.

Use separate databases for Creem test and live environments. Billing summaries and payment queries filter orders by `CREEM_ENVIRONMENT`; credit grants and the usage ledger have no environment column. The account credit balance uses the same owner-scoped grants as generation, including historical entitlements. Switching a shared database between payment environments would mix spendable grants. The application requires migrations 001–008.

History endpoints `/api/account/credits` and `/api/account/payments` return 20 entries per cursor page with `Cache-Control: no-store`. Credit activity combines allocations for a generation into one debit or refund. Monthly expiry entries are inferred from grant dates and have no invented ledger delta. Dates display in UTC.

`/account/history` and `/api/account/history` expose the signed-in owner's saved descriptions, with 20 entries per cursor page and `Cache-Control: no-store`. Successful single and batch generations save all four output formats, language, batch indicator and request time in the same transaction as credit settlement. History storage failure rolls back settlement and follows the generation refund path. Images and raw provider responses are excluded. Guest results use their guest owner and 30-day retention; signing in does not transfer guest history. Previous generated text cannot be recovered because it was not stored.

Retention follows current paid access: an active paid subscription (`active`, `canceled` or `scheduled_cancel`, with `paid_through > now()`) retains all stored history for that account. Queries and cleanup evaluate current subscription access rather than a flag captured at creation. At the end of the final paid period, all descriptions follow a 30-day limit measured from each original request time, including those created during the subscription. Older results disappear from account queries at that point, before scheduled deletion. Canceling renewal keeps full history until paid access ends; overlapping paid subscriptions preserve access through the last eligible paid period. A new subscription protects existing stored history but cannot restore deleted results. Migration 007 adds the history table; migration 008 replaces its retention snapshots with the current-subscription policy and preserves stored description text. Apply both migrations to development and test databases.

Payment history uses verified `billing_payments` records, including renewals. Migration 005 stores transaction amounts from payment evidence for new events. Historical amounts without provider evidence display as an em dash. Creem provides receipts through the billing portal. Order amounts appear on pending checkout summaries and are not substituted for renewal amounts.

## Administration

The operator console is `/admin`, with users, billing, credits, requests, operations and audit pages. Add a comma-separated `ADMIN_USER_IDS` list to the server environment, for example `google:YOUR_GOOGLE_SUBJECT`. The ID is the Google subject prefixed with `google:`; an email address does not grant access. With an empty list the console denies every account. Sign in through `/billing/login?returnTo=%2Fadmin`. An existing account's ID can be obtained from `app_users` after login, or the owned `user_id` on a billing order. Do not add test identities to a live allowlist.

Run `pnpm db:migrate` against the intended database before starting this version. Migration 005 adds account profiles, compensation grants, request metadata, payment evidence, webhook attempts, audit, operations settings, tasks and case records. Historical users are backfilled from existing order/grant owners with a historical marker; profile fields are filled on Google login. The migration runner tracks applied file hashes in `schema_migrations` and serializes execution. Applied migration files must remain unchanged. Back up populated databases before migration.

Administration requires a server-verified Google session and the administrator allowlist on both pages and APIs. GET queries do not create welcome credits. Account suspension blocks generation and new checkout; billing history, portal access, renewals and webhook settlement remain available. Administrator accounts cannot be suspended through this console. Generation and new checkout pause flags are enforced in the server-side usage/order services.

Compensation accepts 1–100,000 whole credits, a reason, an optional expiry and a related reference. The UI previews changes before submission. Actions carry an operation UUID, reject conflicting reuses, and commit business changes with their audit record in one transaction. Failed actions have a failure audit entry when storage is available. Expiry changes, manual debit, editing order/payment status and deleting ledger entries have no operator endpoint. Recovery is restricted to reservations older than five minutes with `reserved` status, and returns allocations to their original grant sources; expired/revoked sources may not increase spendable balance. Extra compensation is a separate audited action.

The billing view links to the Creem dashboard. Refunds, subscription cancellations and provider event redelivery are performed there. The application verifies provider evidence when events arrive; it stores `amount_paid`, currency, refund snapshots and positive refund deltas per event. It does not substitute order amounts for transaction amounts. `paid_at` is the verified payment event time observed by this application; older unknown dates remain missing. Net transaction amount is gross less refunds, before fees and tax. Disputes revoke entitlements but are not invented as cash refunds when a refund amount is absent.

Request records contain server/client IDs, owner identity, language, model name, stage timestamps, normalized result/error codes, a safety outcome and reservation references. Admitted pre-reservation rejections are included. Origin, source-validation, throttle and service-readiness rejections occur before per-request trace insertion; throttle attempts remain in bounded per-bucket counters, including over-limit attempts. Responses expose `X-Request-Id` even when no trace row exists; error messages include a support reference. Image bytes, image URLs, generated text, prompts and raw provider payloads are excluded. Metadata failures do not undo an already settled credit transaction. Historic requests without traces remain available as usage reservations; the UI does not invent old error reasons or durations.

Configure a deployment scheduler to call `GET /api/cron/operations` every five minutes with `Authorization: Bearer CRON_SECRET`. Use a private secret of at least 32 characters. This endpoint recovers up to 500 stale reservations, records a task run and prunes operational metadata. `USAGE_RECOVERY_INTERVAL_MINUTES=5` declares the schedule for the console; it does not create a scheduler. For environments without HTTP cron, run `pnpm usage:recover` every five minutes and `pnpm operations:prune` daily. The operations screen shows the latest run, expected next time and stale-run notice. Platform scheduling remains a deployment step.

Description history and request metadata are excluded from cleanup while their owner has current Pro paid access. When that access expires, all records older than 30 days from their request time become eligible for deletion, including records created during the subscription. Guest history follows the 30-day rule. Existing records follow the same current-access policy. Callback and task metadata are pruned after 90 days. Unresolved service failures and processing requests remain available for investigation. Payment, credit and audit records are excluded from pruning. `GET /api/cron/operations` and `pnpm operations:prune` include description cleanup. The privacy page documents this scope. Operational health shows configuration separately from probes; only the database has a no-charge connectivity probe. Provider readiness, live OAuth, live model generation and real payments require deployment verification with their credentials.

Overview day boundaries use `Asia/Shanghai`; storage uses UTC. Missing historical amounts are reported as excluded transactions. Successful image counts use completion time; success/failure ratios use the cohort of requests created in the selected period that obtained a reservation, including unsettled requests. Guests and signed-in users are distinct identities. Both payment environment filters and separate test/live databases remain necessary.

Validation: `pnpm test:admin` runs administrator workflow tests against `TEST_DATABASE_URL`, whose database name must start with `describe_audit`. Apply migrations to that isolated database before testing. Use `pnpm test`, `pnpm test:billing`, `pnpm lint` and `pnpm build` for the remaining checks. Browser verification uses an isolated local database and temporary signed test sessions, with no authentication bypass in application code.

The account tests run with `pnpm test:billing`, using `TEST_DATABASE_URL`. Browser verification uses isolated test accounts and temporary signed test sessions; no authentication bypass or preview fixture is part of the application routes.
