# 管理后台基本运营规划

规划日期：2026-11-05。依据：项目工作区中的认证、支付、积分、生成、审核与账户查询代码。运行环境、支付凭证和第三方服务连通性属于部署验收范围。

## 目标与范围

面向站长与客服处理五类工作：查看经营情况、查找用户、核对支付权益、处理积分异常、定位生成故障。

首版按一名站长运营设计，提供站长权限；客服角色与角色配置归入后续版本。页面布局采用侧栏、筛选列表、详情页。列表支持时间筛选、状态筛选与游标分页，详情通过用户 ID、订单 ID、交易 ID、请求 ID 建立关联。

## 现有基础与缺口

| 领域 | 代码中的基础 | 后台建设缺口 |
| --- | --- | --- |
| 身份 | Google 登录、JWT 会话、Google subject 用户标识 | 用户档案、登录时间、封禁状态、管理员名单 |
| 支付 | 订单、订阅、支付记录、Creem Webhook 验签与去重 | 每笔交易金额、退款金额、失败回调记录、对账页面 |
| 积分 | 积分批次、预占、完成、退回、撤销与流水 | 人工补偿类型、操作理由、管理员审计记录 |
| 生成 | SeeAPI 审核、Gemini 生成、失败退回积分 | 请求结束时间、耗时、错误码、故障阶段、审核结论摘要 |
| 恢复 | 回收超过五分钟的预占记录的脚本 | 定时任务运行记录、异常队列、后台处理入口 |
| 隐私 | 数据库不保存图片、描述正文与审核结果 | 元数据记录方案、保留周期、隐私文案同步 |

现有 `getUsageStatus` 会创建欢迎积分；后台用户查询应使用读取查询，避免查询行为触发发放。

## 首版功能清单

### 1. 运营概览 `/admin`

首页由指标与待办组成：

- 指标：新增用户、活跃生成用户、生成成功图片数、付费交易数、有效 Pro 用户数、积分消耗。
- 支付金额：展示具有支付凭证的成交额、退款额与成交净额；手续费与税费未入库时，成交净额不命名为到账收入或利润。
- 待办：超时预占、支付到账但权益待核对、Webhook 处理失败、服务错误。
- 趋势：近 7 天、近 30 天；筛选测试环境与生产环境。

验收：每项指标有统计口径，点击待办进入携带筛选条件的列表。缺失数据展示“未采集”，历史数据覆盖范围标注采集起始日。

### 2. 用户管理 `/admin/users`

列表字段：用户 ID、邮箱、创建时间、登录时间、状态、套餐、可用积分、成功生成图片数、付费交易数。

搜索：用户 ID、邮箱；筛选：封禁状态、订阅状态、创建时间。

用户详情分为基本信息、积分、订单与订阅、生成请求、操作记录五个区域。积分区区分欢迎、购买、订阅、人工补偿，以及生效时间、到期时间和下个发放窗口。

操作：封禁、解封、跳转补偿积分。封禁记录原因与操作者；服务端在生成与创建结账入口校验状态。保留用户查看历史账单、管理订阅的入口，避免封禁阻碍取消订阅。

验收：输入用户邮箱可以查到关联订单、积分与请求；封禁后的现有会话无法发起生成和结账。历史邮箱缺失时展示缺失标记，后续登录补齐档案。

### 3. 订单与订阅 `/admin/billing`

包含订单、交易、订阅三个标签页：

- 订单：订单号、用户、商品、创建时间、环境、订单金额、购买时的积分权益、结账状态与关联交易。
- 交易：交易号、订单号、支付时间、实收金额、币种、退款金额、支付渠道状态、权益处理状态。
- 订阅：订阅号、用户、月付或年付、渠道状态、付费有效期、本月积分窗口与待生效窗口。

详情展示支付渠道记录、本地支付记录、积分发放与撤销记录的对应关系。退款和争议形成待办；核验入口连接到 Creem。

首版退款、取消订阅与渠道事件重发在 Creem 管理端执行；本后台展示同步结果。对账异常提供“标记处理中”“记录结论”操作。后台内的退款按钮归入后续版本。

验收：重复支付事件不重复发放积分；历史订单沿用购买时的金额与积分；退款和争议可以追踪至交易及受影响的积分批次。订单状态不提供人工改写入口。

### 4. 积分与补偿 `/admin/credits`

包含用户余额、积分批次、积分流水和异常预占列表。

- 人工补偿：选择用户、积分数、原因、关联订单或请求；可填写到期时间。
- 处理预占异常：检查预占时长、关联请求与结算状态；对符合恢复条件的记录退回积分。
- 流水：关联来源批次、预占、退回、撤销、补偿与管理员操作。
- 补偿预览：显示用户、变更数量、来源与到期规则；提交使用操作唯一标识防止重复。

首版提供增加补偿积分与恢复异常预占。扣减余额、改写购买权益、删除流水归入范围外。误发补偿的撤销功能归入后续版本，撤销上限为该补偿批次的剩余积分。

补偿需要新增积分类型，并让余额查询、消费顺序、用户账户展示与流水查询识别此类型。恢复预占沿用原分配关系；来源批次过期或撤销时，界面展示可用余额的变化，人工补偿作为独立操作。

验收：重复提交不重复补偿；重复恢复不重复退回；处理中或完成的请求不能通过恢复入口获得积分；操作者与原因可追溯。

### 5. 生成与审核记录 `/admin/requests`

列表字段：请求 ID、预占 ID、用户或访客、时间、语言、批量标识、图片数量、结果、失败阶段、耗时、预占积分、退回状态。

结果分类：成功、内容拦截、审核服务失败、模型服务失败、输入无效、额度不足、限流、处理中。请求结果与积分结算状态分栏，避免将“积分已退回”当作故障原因。

详情提供阶段时间线：接收请求 → 输入校验 → 预占积分 → 内容审核 → 模型生成 → 积分结算；通过请求 ID 关联日志、错误码和恢复记录。预占前拒绝的请求也属于统计范围。

数据范围为请求元数据、规范化错误码、审核通过或拦截摘要、模型名称和耗时；图片、Base64、描述正文、供应商原始响应不进入后台记录。隐私政策应反映新增元数据的用途与保留期限。

首版不提供重新生成入口。问题处理路径为定位原因、核对退回、必要时补偿，避免重试产生模型费用与内容留存需求。

验收：用户提供请求 ID 后可查询处理阶段；审核拦截与服务故障区分；失败请求可以核对积分结算。

### 6. 系统与运营任务 `/admin/operations`

- 配置状态：数据库、Google 登录、Creem、Gemini、SeeAPI；展示“配置缺失”“配置齐备”“探测通过”“探测失败”“未探测”。配置齐备与服务连通分栏。
- 任务状态：异常预占恢复的运行时间、处理数量、错误记录和下次计划时间；任务调度由部署平台负责。
- Webhook 状态：接收时间、事件 ID、事件类型、处理结果、错误码、关联订单与处理次数。
- 运营开关：暂停生成、暂停新结账；保留账户、历史账单和订阅管理访问。
- 告警：预占恢复失败、Webhook 失败、生成服务连续失败；首版提供站内待办，邮件或其他消息通道归入后续版本。

密钥通过部署环境管理。页面不展示密钥值；探测结果标注时间，供应商探测区分是否产生费用。

验收：站长能识别缺配置、服务故障与任务停跑；暂停开关在服务端生效；恢复任务提供本次处理结果。

### 7. 管理员与操作日志 `/admin/audit`

首版使用经服务端校验的 Google 用户 ID 管理员名单，站长账户通过部署配置设定。后台页面与接口共享权限校验，权限检查不依赖菜单显示。

操作日志记录操作者、操作时间、目标对象、动作、原因、变更摘要、执行结果与关联操作 ID。封禁、解封、补偿、异常恢复和运营开关写入日志。

状态变更具备权限校验、同源校验、事务约束与幂等处理；管理员写入失败时，业务变更和对应审计记录保持一致。失败尝试进入独立审计记录。

验收：普通登录用户无法访问后台页面和接口；重复提交不产生重复业务变更；日志不提供编辑或删除入口。

## 统计口径

| 指标 | 首版定义 |
| --- | --- |
| 新增用户 | 用户档案创建时间落入统计区间的账户数；历史数据迁入标记为历史账户 |
| 活跃生成用户 | 区间内成功生成过图片的登录用户去重数；访客分栏 |
| 成功生成图片数 | 以完成时间统计成功图片数量；批量以图片计数 |
| 生成成功率 | 成功图片数 ÷ 获得积分预占的请求图片数；处理中单列，并标注尚未结算 |
| 技术失败率 | 审核服务与模型服务失败图片数 ÷ 获得积分预占的请求图片数；内容拦截单列 |
| 付费交易数 | 具有渠道支付凭证的交易数；续费按交易计数 |
| 成交净额 | 区间内实收金额减区间内退款金额；按币种展示，缺证据的金额不参与合计 |
| 有效 Pro 用户 | 查询时符合生成服务权益判定且处于付费有效期的用户去重数；取消但尚在付费期的账户计入 |
| 积分消耗 | 区间内预占扣减减区间内对应退回；补偿、过期和支付撤销分栏 |

数据库存储 UTC 时间；运营日期边界采用 Asia/Shanghai，界面标注时区。支付环境采用隔离数据库；积分表缺少环境字段，后台筛选不能替代数据库隔离。

## 数据建设

| 数据 | 建设内容 |
| --- | --- |
| 用户档案 | `user_id`、邮箱、创建时间、登录时间、账户状态、封禁原因；登录流程维护 |
| 生成请求 | 服务端追踪 ID、客户端请求 ID、owner、预占 ID、阶段、结果、错误码、语言、图片数、模型、阶段时间、结束时间；记录预占前拒绝 |
| 支付金额 | 交易金额、币种、退款金额、渠道支付及退款发生时间、凭证来源；续费金额不从订单价格推算 |
| Webhook 尝试 | 事件 ID、接收时间、类型、结果、错误码、处理次数与关联对象；现有 `billing_events` 保留去重职责 |
| 补偿与审计 | 补偿积分类型、操作唯一标识、原因、管理员、目标与变更摘要 |
| 运营状态 | 暂停开关、任务运行记录、待办状态、处理人和处理结论 |

历史资料处理：用户通过现有 owner 标识建立历史档案；邮箱在登录时补齐。支付金额经渠道证据补录。旧预占记录保留现有状态，失败原因和耗时标注未采集。

建议保留周期：请求与审核摘要 30 天，Webhook 尝试和任务日志 90 天；支付、积分及审计记录的周期在上线验收时确定。分页与组合索引覆盖 owner、时间、状态与事件 ID，避免后台列表执行全表扫描。

## 实施顺序

1. **权限与数据基础**：管理员校验、用户档案、审计、生成元数据、支付金额与Webhook尝试记录。该阶段确定后续指标可用范围。
2. **查询工作台**：用户、订单、交易、订阅、积分、请求列表和关联详情；提供搜索、筛选与分页。
3. **运营处置**：补偿积分、封禁与解封、异常预占恢复、待办处理与暂停开关；验证权限、事务和重复提交行为。
4. **经营概览**：指标、趋势、待办汇总与任务状态；按数据覆盖范围展示历史区间。

首版完成标准：站长可以从用户邮箱或业务编号查清权益来源、支付情况、生成结果与积分去向，并完成补偿、封禁和异常恢复；业务变更有审计记录。
